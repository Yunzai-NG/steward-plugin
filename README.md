# @yunzai-ng/steward-plugin

指令运维：在聊天里重启实例、关机、更新插件、更新内核。全部命令限**主人**。

> 需要 **core ≥ 0.6.3** —— 用到了 `ctx.app.maintenance`（受控地更新插件、请求重启与关机），
> 更新日志与「编译失败则不重载」则要 0.6.3 起才有的 `commits` / `setupError`。

## 命令

| 命令 | 作用 |
|---|---|
| `#重启`（`#重启内核` / `#重启实例`） | 优雅停机，由外部守护拉起 |
| `#关机`（`#停机` / `#关闭实例`） | 优雅停机且不再起来；执行前必先确认 |
| `#更新插件 [名字…]` | 更新指定插件并重载；不写名字则更新全部（本插件自己除外） |
| `#更新自己` | 更新本插件；更新后需重载或重启才生效 |
| `#更新内核`（`#升级内核`） | 经包管理器把内核升到目标版本，之后重启才生效 |
| `#运维状态` | 看这台实例能不能重启、关机，装了几个插件 |

`#更新插件 a b c` 逐个更新点名的几个；写错名字会得到内核那句「没有名为 X 的插件」，不静默跳过。

## 关于「重启」——先读这段

**内核自己没有重启能力。** 它能做的是「优雅停机」，把进程停干净；**再把它拉起来这一步，得靠守护**。从 CLI 0.6.0 起 **`yzng start` 缺省自带守护**（fork 一个子进程跑内核，退出码 75 即重启、0 即收工），所以裸起也能 `#重启`、`#关机`，无需再挂 pm2 / systemd。

- 自带守护（缺省）：`#重启` 停机后立即被父进程拉起，十几秒回来；本插件不再追问确认。
- 外部守护（pm2 / systemd）：以 `--no-supervise` 关掉自带守护、交给它们；退出码 75 同样触发拉起。
- **两者都没有**（`--no-supervise` 且未挂外部守护）：`#重启` 照样停机而没人拉起 —— 机器人就此离线，要你到机器上手动再启动。故探测不到守护时本插件**先问你一句**，回「确认」才动手。这里不能直接拦：探测不到不等于没有守护（Windows 服务一类不留可识别痕迹）。

内核的 `maintenance.canRestart` **不能**用来判断有没有守护 —— `yzng start` 不论有无守护都会接管重启，故它在任何 `yzng start` 起的实例上都为真。它为假只出现在内核被嵌进别的程序、或跑单元测试时。

### 交给 pm2 / systemd（可选）

多数人用缺省的自带守护即可。若你已有 pm2 / systemd，想统一纳管，用 `yzng start --no-supervise` 关掉自带守护那一层，避免套娃（否则 `max_memory_restart` 只量得到空壳父进程）。

pm2 默认 `autorestart`，退出即拉起。但 pm2 之下**没有 TTY，标准输入适配器用不了**，托管前先禁用它。

systemd 单元建议 `Restart=always`（`on-failure` 也行，退出码 75 非零，会拉起）：

```ini
[Service]
Restart=always
Environment=YZNG_HOME=/home/yunzai
ExecStart=/usr/bin/yzng start --no-supervise
```

`YZNG_HOME` 必填 —— 以服务或 pm2 启动时工作目录不是项目目录。

## 关于「关机」

`#关机` 与 `#重启` 走同一条路（优雅停机 + 交给宿主退出），区别只在**退出码**：重启用 75，关机用 0。守护认不认这个 0，取决于用的是哪种守护：

- **自带守护（缺省 `yzng start`）**：天然认得 0，关机即真关，无需任何额外配置。
- **pm2**：默认对任何退出码都拉起，必须在配置里写 `stop_exit_codes: [0]`，否则关了会被立刻拉起来。
- **systemd**：`Restart=on-failure` 天然不拉起零退出；`Restart=always` 要另写 `RestartPreventExitStatus=0`。

挂 pm2 时（即用了 `--no-supervise` 交给它托管）：

```js
// ecosystem.config.cjs
module.exports = {
  apps: [{
    name: "yunzai-ng",
    script: "node_modules/@yunzai-ng/cli/dist/bin.js",
    args: "start --no-supervise",
    stop_exit_codes: [0]   // 让 #关机 真能关掉
  }]
}
```

**关机之后没有任何聊天指令能把它启动回来**，只能到那台机器上手动启动。故这条命令一律先问一句确认，不像 `#重启` 那样只在探测不到守护时才问。

## 更新插件

一条 `#更新插件` 分四步，每步都出声：

1. **收到即回**一句「正在更新 X」。拉代码、装依赖、编译加起来可能几十秒，这期间没反馈的话使用者会以为命令没触发。
2. 每个插件更新完，**把这次拉来的提交折成一个合并转发**发出来，每行形如 `[09-29 01:20] feat: 加一条命令`。批量时一个插件发一个卡片，紧跟在它自己更新完之后，而不是攒到最后 —— 攒在一起认不出谁是谁。平台不支持合并转发时退回逐条贴，只贴最近 5 条。
3. 回一段汇总：谁更新了、谁已是最新、谁失败了。
4. **编译通过的才重载**，重载完再回一句「已生效」。装依赖失败或 `build` 失败的**不重载**，而是明说不重载的原因：那时产物还是旧的，换上去只会把一个跑不起来的插件顶替正在正常工作的那份。

更新日志靠 git 历史取。拉取用的是 `--depth 1`，父链不在本地，故取日志前会按上限（30 条）补拉一次历史；补拉失败只报最新一条，全取不到就不报 —— 这一步失败不影响更新本身。

## 更新内核

`#更新内核` 代跑一次 `yzng update`（不自己重写升级逻辑：那条命令里攒着「只升 cli、其余由它带上来」「剪掉根 package.json 里多余的框架依赖」等一串只有踩过才知道的判断）。装好后**必须重启才生效**——新内核代码不能热替换进正在跑的进程。若此时重启不可用，会明说「现在跑的仍是旧内核」。

目标版本在配置里填，只收 dist-tag（`latest`）或具体版本号（`0.6.1`），**不收 `^0.6.0` 这类范围**——那些符号在命令行里另有含义。

## 配置

| 项 | 缺省 | 说明 |
|---|---|---|
| 允许指令重启 | 开 | 关掉后 `#重启` 只回说明、不动实例 |
| 允许指令关机 | 开 | 关掉后 `#关机` 只回说明、不动实例 |
| 撞上本地改动时 | 停手不改 | 插件目录有未提交改动时：停手 / 暂存 / 丢弃 |
| 更新后装依赖 | 开 | package.json 变过时必须装 |
| 更新后自动重载 | 开 | 关掉则要去面板插件页手动重载 |
| 内核目标版本 | latest | dist-tag 或具体版本号 |
| 内核更新超时 | 15m | 国内网络冷装十几分钟不罕见 |
| 更新内核后自动重启 | 开 | 关掉则更新完只提示，自己决定何时重启 |
